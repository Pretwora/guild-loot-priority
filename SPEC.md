## 1. Что строим и зачем

Гильдия играет на приватном сервере Sirus.su, реалм x3, ID гильдии 7868, рейды на 25 человек. Лут распределяется консулом (loot council): решение принимает совет офицеров, а не автоматический счётчик очков.

Нужен публичный статический дашборд на GitHub Pages, который отвечает рейд-лидеру на два вопроса:

1. **Кто заслужил** — сводный рейтинг по посещаемости, эффективности и уже полученному луту.
2. **Кому эта вещь** — по каждому упавшему предмету отсортированный список кандидатов с расшифровкой, почему они в таком порядке.

Ключевая рамка: **система — советник, а не судья.** Она готовит и обосновывает решение, принимает его совет. Любая архитектурная развилка решается в пользу прозрачности и объяснимости, а не в пользу автоматизма.

## 2. Принципы, которые нельзя нарушать

1. **Сырьё неизменяемо.** Ответы API коммитятся как есть, никогда не редактируются и не удаляются. Всё производное пересчитывается с нуля из сырья при каждом прогоне. Никакого инкрементального состояния в производных данных.
2. **LLM не считает числа.** Весь скоринг — детерминированный Python. Языковая модель допускается только для формулировки текстовых пояснений и для разметки неоднозначных предметов, причём результат разметки коммитится в репозиторий как данные и ревьюится человеком.
3. **Все веса и константы — в `config/weights.yml`.** В коде не должно быть ни одного магического числа из формул.
4. **Сбор отделён от пересчёта.** Два независимых воркфлоу. Сломанный скоринг не должен останавливать накопление истории — историю задним числом не восстановить.
5. **Никаких секретов в репозитории.** Дашборд публичный, репозиторий публичный.
6. **Формула замораживается на игровой тир.** Изменение весов посреди тира обесценивает накопленное и разрушает доверие к системе. Менять только через PR с описанием причины.
7. **Каждое число на дашборде должно быть объяснимо** одной фразой на человеческом языке. Если компонент скоринга невозможно объяснить рейдеру — он не нужен.

## 3. Источник данных

### 3.1 Эндпоинты

Официального публичного API у Sirus нет — поддержка это подтверждала. Есть внутренний JSON, на котором работают сторонние боты. Эндпоинты рабочие, но недокументированные и могут измениться без предупреждения.

```
GET https://sirus.su/api/base/{realm}/progression/pve/latest-boss-kills?guild={guildId}&lang=ru
    → лента последних убийств боссов гильдии
      ожидаемые поля записи: id (record_id), mapId, encounter_id, время

GET https://sirus.su/api/base/{realm}/details/bossfight/{recordId}?lang=ru
    → детали одного убийства
      ожидаемые поля: players[] (name, class_id, spec, dps, hps)
                      loots[]   (item.entry, item.quality, item.name)
```

`{realm}` — либо слаг из адреса страницы гильдии (`x3`), либо числовой ID. Известные числовые ID из сторонних ботов: 9 = Scourge x2, 22 = Neverest x3, 42 = Soulseeker x1, 57 = Sirus x5. Для x3 наиболее вероятен 22, но проверяется разведкой.

Публичные страницы для ссылок с дашборда:

```
https://sirus.su/base/guilds/{realm}/{guildId}
https://sirus.su/base/pve-progression/boss-kill/{realm}/{recordId}
https://sirus.su/base/item/{itemEntry}/{realm}
```

### 3.2 Схема не подтверждена вживую

Имена полей выше восстановлены по чужому клиентскому коду, а не по живому ответу. **Этап 0 — разведка. Нормализатор до неё не писать.**

### 3.3 Правила обращения с чужим API

- Не чаще одного запроса в 1.5 секунды. Параллельных запросов нет.
- Ретраи только на 429 и 5xx, экспоненциальный бэкофф с джиттером, максимум 4 попытки.
- Реалистичный User-Agent, `Accept: application/json`.
- Детали кила скачиваются ровно один раз: если файл на диске есть — запроса нет.
- Опрос ленты — не чаще раза в 30 минут.

### 3.4 Чего API не даёт (закрывается вручную)

| Пробел | Как закрываем |
|---|---|
| Кто получил предмет | Ручной ввод рейд-лидером после рейда, этап 4 |
| Кто сидел в бенче / опоздал | Ручной ввод там же |
| Метрики танков (угроза, полученный урон) | Никак. Танки получают нейтральный перформанс |
| История глубже ленты | Никак. История начинается с первого прогона коллектора |
| Текущая экипировка персонажей | Никак на первых этапах. Прокси — время с последней выдачи в слот |

## 6. Схемы данных

### 6.1 roster.yml

Связывает персонажей с игроками. Без этого файла система разваливается на второй неделе: на 25-ке один человек ходит разными персонажами, а API знает только персонажа.

```yaml
players:
  - id: grimm                 # канонический идентификатор игрока
    display: Гримм
    rank: member              # trial | member | officer
    joined: 2026-06-14
    characters:
      - name: Гримм           # ровно как в API
        class_id: 1
        spec: fury
        role: dps             # dps | heal | tank
        main: true
      - name: Гриммхил
        class_id: 5
        spec: holy
        role: heal
        main: false
```

Неизвестные персонажи, встреченные в логах, не молча игнорируются — они попадают в отчёт сборки как «требуют добавления в ростер» и выводятся на дашборде отдельным блоком.

### 6.2 attendance.yml

Только то, чего нет в логах.

```yaml
2026-08-30:
  bench: [nirva, kettle]      # пришли, посадили — засчитывается как полное присутствие
  late: [dorn]                # засчитывается по фактической доле килов
  excused: [milk]             # предупредил заранее, вечер не идёт в знаменатель
```

### 6.3 loot_log.csv

```csv
date,record_id,item_entry,item_name,player,award_type,note
2026-08-30,4821553,50818,"Печать Багрового Ужаса",grimm,bis,
2026-08-30,4821553,50722,"Наплечники Разложения",elya,offspec,
2026-08-30,4821560,50274,"Знак Утопающего",,shard,никому не нужен
```

`award_type` и множитель к весу предмета:

| Значение | Множитель | Смысл |
|---|---|---|
| `bis` | 1.0 | в основной спек |
| `offspec` | 0.25 | в запасной спек |
| `free` | 0.0 | никто не нуждался, отдали лишь бы не пропало |
| `shard` / `de` | — | не учитывается вообще |
| `trade` | 1.0 | передан позже, дата передачи в `note` |

Разделение типов — не бюрократия. Без него человек, взявший никому не нужную оффспек-вещь, просядет так же, как взявший БиС-оружие. Это первое, на что пожалуются.

## 7. Формулы

Все константы ниже — значения по умолчанию для `config/weights.yml`.

### 7.1 A — посещаемость, 0..1

Окно: последние 8 недель или последние 12 рейд-вечеров, что больше.

Вес вечера: `λ^days_ago`, λ = 0.98 (полураспад около 34 дней).

Кредит за вечер:

| Ситуация | Кредит |
|---|---|
| был на ≥ 80% килов вечера | 1.0 |
| был на 30–80% килов | фактическая доля |
| бенч | 1.0 — человек пришёл, сажали его вы |
| отпросился заранее | вечер исключается из знаменателя, но не более двух подряд |
| не пришёл | 0 |

```
A = Σ(вес_вечера × кредит) / Σ(вес_вечера)
```

Сжатие к среднему для малой выборки:

```
conf  = min(1, вечеров_посещено / 6)
A_eff = A × conf + A_медиана_гильдии × (1 − conf)
```

Без этого новичок с двумя рейдами получает честные 100% и обходит того, кто ходит полгода.

### 7.2 P — перформанс, 0..1

Для каждого кила: перцентиль игрока среди всех записей **того же спека на том же боссе** за текущий тир.

```
p = ранг / (n − 1)
```

При `n < 5` записей для сравнения `p = 0.5` — недостаточно данных значит нейтрально, а не плохо.

Метрика по роли: dps-спеки — по dps, хилы — по hps, **танки — фиксированно 0.5**. API не отдаёт ни угрозу, ни полученный урон, а dps танка ничего не измеряет. Честнее признать, что мы этого не видим, чем считать мусор и ранжировать по нему людей.

Итог — медиана перцентилей за последние 12 килов. Медиана, а не среднее: один провальный пул не должен ронять человека на месяц.

### 7.3 L — полученный лут

```
L = Σ (вес_предмета × множитель_типа × 0.985^days_ago)
```

Полураспад около 46 дней. Веса по слотам:

| Слот | Вес |
|---|---|
| двуручное оружие, тир-токен, тринкет | 1.0 |
| одноручное и дальнобойное оружие, грудь, голова, ноги | 0.8 |
| плечи, руки, пояс, ботинки, наручи | 0.6 |
| кольцо, плащ, шея | 0.5 |
| рецепты, расходники | 0.1 |

```
L_norm = clip(L / (медиана_по_гильдии + ε), 0, 2)
```

### 7.4 Итоговый рейтинг игрока

```
S = 100 × (0.7 × A_eff + 0.3 × P) / (1 + 0.35 × L_norm) × rank_gate
```

`rank_gate`: триал 0.6, состав 1.0. Триал может расти внутри своей группы, но не перепрыгивает постоянный состав.

Вклад перформанса ограничен 30% сознательно. Выше — и топ-дпс в лучшей экипировке начинает забирать всё, разрыв растёт сам себя усиливая, а система превращается в машину неравенства.

### 7.5 Fit — соответствие предмета игроку, 0..1

```
F = need × slot_gap × set_bonus
```

- `need`: 1.0 если предмет подходит основному спеку, 0.3 — запасному, 0 — не подходит.
- `slot_gap`: прокси нужды по слоту, пока нет данных об экипировке. Никогда не получал в этот слот — 1.0, получал недавно — ближе к 0. Функция от недель с последней выдачи в слот, насыщение на 12 неделях.
- `set_bonus`: 1.25 если токен закрывает 2- или 4-сет, иначе 1.0.

### 7.6 Кандидаты на предмет

Сортировка по `S × F`, показывать топ-5 с разбивкой компонентов. Не показывать одно итоговое число без расшифровки — именно расшифровка делает систему защитимой в споре.

## 8. Правила «кому нужен предмет»

Каскад, применяется по порядку:

1. **Тип брони и слот** отсекают классы. Ткань — маг, чернокнижник, жрец. Кожа — друид, разбойник. Кольчуга — охотник, шаман. Латы — воин, паладин, рыцарь смерти. Применяется к слотам голова, плечи, грудь, наручи, руки, пояс, ноги, ботинки.
2. **Основной стат.** Сила — воин, паладин, рыцарь смерти. Ловкость — разбойник, охотник, друид-кот, шаман-усиление. Интеллект — касты и хилы.
3. **Вторичные маркеры.** Дух и mp5 — хил. Рейтинг защиты, уклонение, парирование, блок — танк. Меткость вместе с экспертизой — ближний бой. Сила заклинаний с ускорением — каст. Пробивание брони — друид-кот, разбойник, охотник, воин-оружие.
4. **Оружие, кольца, плащи, шеи, тринкеты** — без типа брони, только по статам и типу оружия с учётом классовых ограничений.
5. Всё, что не разошлось однозначно, идёт в `item_overrides.yml` и подсвечивается на дашборде как требующее разметки. Молча угадывать нельзя.

**Источник характеристик предметов.** Sirus — кастомный сервер со своими предметами, которых нет в открытых дампах 3.3.5. Схема гибридная: офлайн-дамп как основа, неизвестные `entry` дотягиваются по одному со страницы предмета на их сайте и кешируются в `data/items/` навсегда. Массово их сайт не парсить.

БиС-листы по спекам вести как версионированный JSON с указанием источника, обновлять раз в тир. Автоматически ниоткуда не тянуть.

## 9. Дашборд

### 9.1 Экраны

1. **Приоритет** — главная. Игрок, класс, посещаемость, перформанс, последний лут, итоговый рейтинг, изменение с прошлого рейда.
2. **Лут-борд** — матрица «слот × игрок»: что закрыто, что нужно. Экран, ради которого всё затевалось, — на нём совет принимает решение быстрее всего.
3. **Рейды** — история вечеров, кто был, кто в бенче, кто не пришёл.
4. **Игрок** — карточка: посещаемость во времени, перформанс по боссам, история полученного.
5. **Как это считается** — открытая страница с формулами и текущими весами, генерируется из `weights.yml`, а не пишется руками. Публичный дашборд без объяснимой формулы производит конфликты, а не решает их.

### 9.2 Технически

Vite + React, читает один статический `dashboard.json`. Бэкенда нет. Таблицы должны работать при 40+ игроках без пагинации, с сортировкой по любой колонке.

### 9.3 Направление оформления

Прежде чем писать компоненты, набросать план дизайна: палитра, типографика, сетка — и проверить его на неслучайность.

Предметная рамка: это не портфолио и не лендинг, а рабочий инструмент, открытый на втором мониторе в час ночи, когда двадцать пять человек ждут решения по луту. Плотность важнее воздуха, читаемость с расстояния важнее изящества, никаких анимаций появления.

Цвета классов WoW обязательны — их все читают мгновенно, это готовый словарь, которым грех не воспользоваться. Но фон и вся остальная палитра должны быть подобраны так, чтобы девять классовых цветов на одном экране не превратились в кашу; это главная реальная задача оформления, и её стоит решать осознанно, а не брать тёмную тему по умолчанию.

Чего избегать: одинаковых скруглённых карточек с одинаковой тенью, разреженных ALL-CAPS подписей над каждым заголовком, стрелок в конце ссылок, градиентов как украшения. Это выдаёт сгенерированную страницу.

Обязательный минимум качества: работает на телефоне, видимая фокусировка с клавиатуры, уважение к `prefers-reduced-motion`, контраст по AA.

## 10. Подводные камни

- **Метрики наказывают полезных.** Тот, кто бегает механику, переключается на аддов или танкует, просядет по всем счётчикам. Поэтому есть `adjustments.yml` и потолок в 30% на перформанс. Не убирать ни то, ни другое.
- **Твинки.** Без `roster.yml` рейтинг ломается почти сразу.
- **Смена спека.** Игрок может перекатиться внутри тира — история перформанса за старый спек не должна тянуться в новый.
- **Неофициальный API** может измениться или закрыться. Коллектор обязан переживать смену схемы без потери уже собранного: сырьё лежит как есть, а падать может только нормализатор.
- **Cron в GitHub Actions неточен**, опоздания на 10–15 минут нормальны. Расписание работает только с ветки по умолчанию.
- **Часовые пояса.** Килы приходят с серверным временем, рейд-вечера считаются по нему. Не смешивать с UTC в границах вечера.
- **10-ки и другие составы.** Гильдия может ходить и десятками — они не должны попадать в статистику 25-ки. Отфильтровать сразу, как только станет понятно, по какому полю это определяется.

## 11. Что уточнить у заказчика

- Вывод разведки API, если ещё не приложен.
- Список состава с классами, спеками и твинками для первичного `roster.yml`.
- Дата начала текущего тира — граница для сравнения перформанса.
- Порог триала: сколько рейдов до перевода в состав.
- Стоит ли показывать сырые цифры dps публично. Значение по умолчанию — только перцентили внутри спека, решение обратимое переключателем в конфиге.
