# Решения, расхождения и открытые вопросы к заказчику

Собрано по итогам этапов 0–4. Что разошлось с ТЗ, что решено по умолчанию (обратимо,
через конфиг) и что требует твоего слова. Спека требует остановок на 🛑 — вот они,
все в одном месте, с уже готовым дефолтом, чтобы систему можно было увидеть в работе.

## Расхождения API с ТЗ (правил документ, не код — раздел 0)

Полная схема — в [api-schema.md](api-schema.md). Кратко:

1. **Реалм** — слаг `x3` работает напрямую (числовой id x3 = 22).
2. **Время кила** — `timeEnd`/`killed_at` (серверное локальное). Поле `time` в ТЗ было
   принято за время кила, а это длительность боя.
3. **`role` и `spec` — целые**, не строки. role: 1 танк / 2 хил / 3 dps. spec — индекс
   вкладки талантов; идентичность спека = `(class_id, spec)`.
4. **Получателя лута в API нет** — ручной ввод (этап 4) остаётся, не переписан.
5. **`itemset[]` игрока** отдаёт текущий тир-сет и число частей — используем в `set_bonus`
   напрямую, а не эвристикой.
6. **Карточки предметов** доступны JSON-эндпоинтом `tooltip/item/{entry}` (слот, статы,
   тип брони) — каскад раздела 8 считается автоматически. Кеш `data/items/`, качаем по одному.
7. **История доступна пагинацией** (`meta.total=1000`, 20 недель), хотя ТЗ считало, что
   история начинается с первого прогона. Добавлен опциональный `collect.py --backfill`.

## Решения

### 1. ✅ РЕШЕНО — 10-ки, 25-ки и совокупность раздельно

`player_count` за неделю: `{10: 20, 9: 2, 25: 2, 24: 1}` — текущий контент Тир 4:
Каражан (10) + Груул/Маг (25). По твоему ответу сделаны **три ладдера** (переключатель на
дашборде): «10 + 25», «10-ки», «25-ки». Каждый пересчитывает посещаемость/перформанс/лут в
своих рамках. `config.json → raid_night.count_raid_sizes` управляет, какие размеры вообще в
зачёте (сейчас оба).

### 2. Два непересекающихся состава по 10 — проверь автораспределение

Что нашлось: гильдия водит рейд ДВУМЯ фиксированными десятками. В логах вечер 30.08 и вечер
31.08 не имеют **ни одного общего игрока**, а на 25-ку (27.08) оба состава сходятся вместе.
API знает только персонажей, поэтому я по этим данным сам разбил игроков на «команду A»
(ходили 30.08) и «команду B» (ходили 31.08) — это поле `team` в `roster.yml`.

Зачем это нужно: посещаемость честнее считать по знаменателю СВОЕЙ команды. Если этого не
делать, игрок команды B получит «прогул» за вечер команды A, на который его никто и не звал.
Поэтому вечер чужой команды у игрока помечается `team_off` и не идёт в знаменатель.

**Что от тебя нужно:** глянь в `roster.yml`, верно ли я разложил людей по командам A/B, и
не будет ли третьего состава или ротации между командами. 12 человек стоят `team: null`
(засветились только на общей 25-ке) — если кто-то из них на самом деле в A или B, проставь.

### 3. Дата начала тира (`config.json → tier.start`) — объяснение ниже

«Тир» — это фаза контента: набор рейдов, открытых вместе, и соответствующий уровень
экипировки (здесь Тир 4 = Каражан/Груул/Магтеридон). «Дата начала тира» — когда эта фаза
открылась на сервере. Зачем: перформанс сравнивает игрока с парсами **только текущего тира**
— если подмешать старые парсы (когда шмота было хуже), сравнение поедет. Сейчас `null` =
сравниваем по всей доступной истории. Пока история короткая (с первого прогона коллектора),
это без разницы. Заполнять есть смысл, если будешь добирать историю через прошлый тир.

### 4. Порог триала (`config.json → trial.raids_to_member`) — объяснение ниже

В системе есть ранги `trial | member | officer` (в `roster.yml`). У триала множитель к
приоритету лута `0.6` (`rank_gate`) — чтобы новичок на испытательном не перепрыгивал
постоянный состав по луту, но рос внутри своей группы. «Порог триала» = сколько рейдов до
перевода в состав. В коде он НЕ используется: перевод делаешь ты руками, меняя `rank` в
ростере. Значение нужно только чтобы показать правило на странице «Как считается». Если у вас
нет формального испытательного срока — оставь `null` и забудь.

### 5. Публиковать ли сырые dps (`config.json → display.show_raw_dps`) — объяснение ниже

Перформанс на дашборде показан как **перцентиль внутри твоего спека** («ты в 80-м перцентиле
среди Стрельба-охотников на этом боссе»), а не абсолютным числом. Вопрос: показывать ли на
публичном дашборде ещё и сырые dps/hps (например «28 837 dps»).

Зачем это выбор: сырые dps — это публичный лидерборд по числам. Он провоцирует драму (люди
залипают на абсолютных цифрах и сравнивают классы, которые сравнивать некорректно), а
перцентиль-внутри-спека честнее и спокойнее. **Дефолт `false`** (только перцентили). Хочешь
показывать голые цифры всем — поставь `true`, решение обратимое.

### 6. ✅ РЕШЕНО — автоматическая атрибуция лута из API

По твоей наводке на «Последние действия»: нашёл эндпоинт `statistics/{name}/latest-actions`
с событием `obtaineditem` (получил предмет: entry + время). Игрок считается получателем
рейдового дропа, если он был на киле И получил этот предмет в окне после кила
(`loot.attrib_window_hours: 6`). Пересечение с дропом кила отсекает не-рейдовые получения
(крафт, значки).

Работает: на текущих данных **23 из 68** дропов распознаны автоматически и уже проставлены
на дашборде (лут-борд, штраф за лут, история игрока — с пометкой «авто»). Остальные — в
основном шардованные (никто не «получал», сигнала нет) или уехавшие за окно ленты; на будущее
30-минутный сборщик ловит каждое событие сразу. Ручной ввод остаётся только для этих остатков
и для правок: `loot_log.csv` перекрывает авто. Собирает `tools/collect_actions.py`.

Эквип-снимки как источник я убрал — ты верно сказал, что «надел/не надел» нестабильно.

### 7. 🛑 Шаблон issue раздачи лута (остаётся, но теперь для меньшинства)

Ручной ввод теперь нужен только для дропов, что не распознались автоматически. Формат issue —
в [`.github/ISSUE_TEMPLATE/loot.md`](../.github/ISSUE_TEMPLATE/loot.md), заполняются только
«игрок» и «тип», валидация против дропа кила. Автосоздание issue пока НЕ включено — глянь
эргономику. Разбор при закрытии готов (`loot-intake.yml`).

## Что нужно от тебя данными

- **`roster.yml`** — автосид один-персонаж-один-игрок. Объедини твинков, проставь `display`,

- Разметка предмета, который каскад не развёл (`item_overrides.yml`) — сейчас 1 шт.
  («Сумка владыки Запределья» — это сумка, не шмот; можно просто игнорировать).

## Настройки репозитория (этап 1)

`Settings → Actions → General → Workflow permissions` → **Read and write** — иначе пуш из
`collect.yml` упадёт. Блок `permissions` в воркфлоу умеет только урезать права, не расширять.
GitHub Pages: `Settings → Pages → Source: GitHub Actions`.

## Что осознанно НЕ сделано в первой версии

- **БиС-листы по спекам** (раздел 8) — `need` считается прокси по основному стату/маркерам.
  Точность вырастет, когда появятся версионированные БиС-JSON. Заготовка формата — вопрос
  отдельной итерации.
- **Этап 5** (текстовые расшифровки LLM) — вне объёма первой версии (ТЗ), заглушка в
  `core/narrate.py` даёт детерминированные фразы без LLM.
- **Тонкая обработка щитов/реликвий/тир-токенов** в каскаде — редкие случаи уходят в
  `item_overrides.yml`.
