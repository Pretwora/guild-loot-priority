## Лента килов — `latest-boss-kills`

Верхний уровень:

```
data:       list[25]     ← сами килы (текущая неделя)
links:      {first, last, prev, next}   ← next=null в дефолтном ответе
meta:       {current_page:1, from:1, to:25, per_page:50, last_page:20, total:1000, path}
weeks:      list[48]      ← справочник недель тира (week/from/to/range)
week:       {from, to}    ← активное окно (по умолчанию текущая неделя)
instances:  list[25]      ← справочник инстансов и боссов (encounter journal)
selected:   null
encounter:  null
```

`find_records()` коллектора берёт `data` → список. **Проверено на живом ответе — работает без правок.**

### Запись кила (`data[i]`)

```jsonc
{
  "id": 9405611,               // record_id — ключ детали, качаем bossfight/{id}
  "encounter_id": 0,           // индекс босса внутри инстанса (0..N)
  "difficulty": 0,             // режим сложности (см. ниже, значение неоднозначно)
  "guildId": 7868,             // лента уже отфильтрована по нашей гильдии
  "equipment": 253,            // средний ilvl состава на киле
  "guild": { "id", "name", "leader?", "level" },
  "time": "03:29",             // ⚠️ длительность боя, НЕ время кила
  "timeEnd": "2026-08-31 23:50:30",  // ← ВРЕМЯ КИЛА (серверное локальное)
  "mapId": 838,                // инстанс (см. таблицу инстансов)
  "achievements": "6896,",     // строка id ачивок через запятую (может быть "")
  "player_count": 10,          // ← РАЗМЕР РЕЙДА
  "healers": 2,
  "tanks": 1
}
```

### Детали кила — `details/bossfight/{id}`

Тело завёрнуто в `data{}` (плюс на верхнем уровне `order`, `encounter`):

```jsonc
{
  "data": {
    "boss_name": "Гогонаш",
    "map_name": "Тол'Гародская тюрьма",
    "killed_at": "2026-08-31 23:50:30",   // = timeEnd ленты
    "fight_length": "03:29",              // = time ленты
    "duration": 209,                       // секунды
    "difficulty": 0,
    "attempts": 1,
    "guild": { "id", "name", "level" },
    "players": [ /* см. ниже */ ],
    "loots":   [ /* см. ниже */ ],
    "achievements": [ { "entry", "quality", "name", "icon", "points" } ]
  },
  "order": 34,
  "encounter": 0
}
```

### Игрок (`players[i]`)

```jsonc
{
  "guid": 2929,           // стабильный id персонажа на сервере
  "name": "Серёжка",      // имя персонажа — ключ для roster.yml
  "level": 80,
  "class_id": 2,          // класс WoW (см. таблицу классов)
  "race_id": 10,
  "gender": 1,
  "spec": 0,              // ⚠️ ЦЕЛОЕ — индекс спека (0..3), НЕ строка "holy"
  "role": 2,              // ⚠️ ЦЕЛОЕ — 1=танк, 2=хил, 3=dps
  "ilvl": 251,
  "category": 90016,      // назначение неясно, сохраняем как есть
  "dps": 138,
  "hps": 5771,
  "guild": { "id", "name", "level" },   // может быть ДРУГАЯ гильдия (пуги)
  "zodiac": { "id", "name" },           // серверная механика, для скоринга не нужно
  "itemset": [ { "id", "name", "count" } ]  // текущий тир-сет игрока и число частей
}
```

**Маппинг `role` (выведен из образца, сверен с `tanks`/`healers`):**

| role | значение | пример |
|---|---|---|
| 1 | tank | Мозол (DK, Кровь, dps 2754) |
| 2 | heal | Серёжка (Pal, Свет, hps 5771), Сонечко (Priest, hps 6927) |
| 3 | dps  | остальные |

**`spec` — целое (индекс вкладки талантов).** Идентичность спека для скоринга = пара
**`(class_id, spec)`**. Имя спека на русском доступно в `itemset[].name`
(префикс до `|n|`, напр. «Баланс», «Стрельба», «Неистовство»), но только если у игрока
есть тир-части. Каноничный маппинг `(class_id, spec) → человекочитаемое имя` ведём в
`config/specs.yml` (не тянем из itemset — оно ненадёжно).

**`itemset`** — прямой подарок для скоринга: даёт текущий тир-сет и число частей →
используем в `set_bonus` (раздел 7.5 ТЗ), не гадаем.

### Лут (`loots[i]`)

```jsonc
{
  "entry": 158159,
  "count": 1,
  "item": {
    "entry": 158159,
    "quality": 4,            // 4=эпик, 3=рарный. ЦЕЛОЕ (в отличие от achievements, где "")
    "icon": "https://cdn3.scourge.tech/icons/….png",
    "name": "Посох ярости природы",
    "color": "a335ee",       // цвет качества
    "realm_id": 22
  }
}
```

⚠️ **Ни слота, ни типа брони, ни типа оружия в ответе нет.** Слот и статы предмета
берём из карточки предмета (`data/items/`, раздел 8 ТЗ) — в дропе только имя/качество/иконка.

⚠️ **В `loots[]` попадает не только шмот:** в образце были «Очки доблести»
(entry 160000, **quality 4**, count 30) и «Почетный значок» (quality 3, count 3).
Фильтр «качество 4+» из ТЗ поймал бы валюту. Правило кандидата на выдачу:
`quality >= 4 AND count == 1 AND entry не в списке валют` (`config/currency_denylist`).
Шмот всегда падает по одному; валюта/значки — пачками.

## Пагинация и глубина истории

Дефолтный ответ ленты — **только текущая неделя** (`week`), 25 килов. ⚠️ **`?page=N` историю
НЕ листает** (страница 2 пустая), а `meta.total=1000` / `last_page=20` — это, судя по всему,
глобальный счётчик реалма, не история гильдии. История листается **неделями**:

```
GET …/latest-boss-kills?guild=7868&lang=ru&week_from=2026-08-20&week_to=2026-08-27
    → килы за указанную неделю (окно в ответе меняется на этот диапазон)
```

Значения недель есть в `weeks[]` дефолтного ответа (`current`, `previous`,
`last_four_weeks`, и явные даты). Но параметр `week=<value>` в этом эндпоинте **игнорируется**
— работает именно пара дат `week_from`/`week_to`.

**Расхождение с ТЗ (раздел 10):** ТЗ считает, что историю задним числом не восстановить.
По факту прошлые недели доступны через `week_from`/`week_to`. `collect.py --backfill --weeks N`
(по умолчанию выключен, плановый прогон не трогает) шагает назад по неделям и сидирует историю.

## 🛑 Критическое расхождение: гильдия ходит НЕ 25-ки

ТЗ построено на рамке «рейды на 25 человек» (раздел 1) и требует (раздел 10) сразу
отфильтровать 10-ки, чтобы не пачкать статистику 25-ки. **Живые данные это опровергают:**

```
player_count по последней неделе:  {10: 20, 9: 2, 25: 2, 24: 1}
```

Это не «случайно собрали 10-ку». Текущий контент — **Тир 4 (TBC): Каражан — это
10-местный рейд по дизайну**, а Груул и Магтеридон — 25-местные. То есть основной
объём прогресса гильдии сейчас физически 10-местный.

Если применить фильтр «только 25» из ТЗ буквально — на дашборде останется **3 кила**,
и инструмент бесполезен. Это решение заказчика, не моё (раздел 0: «не угадывать за него»).
Реализовано как **конфиг** `ladder.raid_sizes` в `config/config.json`:

- дефолт сейчас — **включить все размеры**, каждый рейд-вечер помечается своим размером,
  чтобы систему можно было увидеть в работе;
- переключение на «только 25» — одна строка в конфиге.

**Вопрос заказчику:** засчитывать ли Каражан (10) в тот же ладдер, что Груул/Маг (25),
или вести раздельные ладдеры по размеру? До ответа держим дефолт «всё вместе, с меткой размера».

## Карточка предмета (этап 4, раздел 8)

Найден JSON-эндпоинт (в дропе слота/статов нет, берём отсюда):

```
GET https://sirus.su/api/base/x3/tooltip/item/{entry}?lang=ru   → {item, auctionhouse, transmogrification}
GET https://sirus.su/api/base/x3/details/item/{entry}?lang=ru   → расширенный (item, tooltip, tabs, ...)
```

Берём лёгкий `tooltip`. Ключевые поля `item{}`:

| Поле | Смысл |
|---|---|
| `inventory_type` | **слот** (WoW enum: 1 голова, 3 плечи, 5/20 грудь, 6 пояс, 7 ноги, 8 ботинки, 9 наручи, 10 руки, 11 палец, 12 тринкет, 13/21/22 оружие 1H, 14 щит, 15/26 дальнобойное, 16 плащ, 17 двуручное, 2 шея) |
| `class` / `subclass` | класс предмета (2 оружие, 4 броня) и подкласс. Броня: subclass 1 ткань, 2 кожа, 3 кольчуга, 4 латы |
| `type` | человекочитаемый тип: «Латы», «Ткань», «Древковое» |
| `required_class` | битовая маска классов (или -1 = любой) — авторитетно, когда задана |
| `stat_type1..10` / `stat_value1..10` | статы (enum: 3 ловкость, 4 сила, 5 интеллект, 6 дух, 7 выносливость, 12 защита, 13 уклонение, 14 парирование, 31 меткость, 36 ускорение, 37 экспертиза, 38 сила атаки, 44 пробивание брони, 45 сила заклинаний, 43 mp5) |
| `itemset_data` | принадлежность к сету |
| `quality`, `item_level`, `name`, `icon` | как в дропе |

Кешируем в `data/items/{entry}.json` навсегда (карточки одного предмета не меняются),
качаем по одному, с той же вежливостью 1.5с. Массово сайт не парсим (раздел 8 SPEC):
`tools/fetch_items.py` добирает только те entry, что реально упали и ещё не в кеше.

Слот, тип брони и статы → каскад «кому нужен предмет» (раздел 8) считается детерминированно.
Что не развелось однозначно — в `item_overrides.yml` + подсветка на дашборде.

## Атрибуция лута — лента «Последние действия» (этап 4)

Получателя в дропе кила нет, но лента действий персонажа отдаёт событие получения
предмета с абсолютным временем. Это стабильный источник (обновляется сразу после
выдачи, не зависит от того, надел ли игрок вещь):

```
GET https://sirus.su/api/base/{realm}/statistics/{name}/latest-actions?profile=true
    → список событий персонажа, новые сверху
```

Событие получения предмета:

```jsonc
{
  "type": "obtaineditem",
  "guid": 210460,
  "datetime": "2026-08-31T21:52:42.000000Z",   // абсолютный UTC
  "id": 226157875,                               // уникальный id события (для дедупа)
  "action": { "entry": 117528, "quality": 4, "name": "Наголенники Малорна", "icon": "…" }
}
```

Есть и `type: "bosskill"` (`action.bossfight_id`, `boss_name`, `attempts`) и `achievement`.

⚠️ `obtaineditem` срабатывает на ЛЮБОЙ полученный предмет (крафт, значки, не только рейд).
Поэтому получателем рейдового дропа считаем игрока только если он **был на киле** И получил
именно этот `entry` в окне после кила (`loot.attrib_window_hours`). Пересечение с `loots[]`
кила отсекает не-рейдовые получения. Снимки ленты — неизменяемое сырьё
(`data/raw/actions/`), собирает `tools/collect_actions.py`, дедуп по `id` события.

Подтверждает серверное смещение: кил `killed_at` 23:50 (локально) = событие `20:50Z` → UTC+3.

## Детальный лог боя (этап 3+, эффективность)

```
GET https://sirus.su/api/base/{realm}/details/bossfight/{id}/combatlog   → ~1 МБ/бой
```

Структура: `players{guid: {dps, hps, taken, deaths, auras, targets}}`, `casts[]` (все
прожатия: spellId, spellName, sourceGuid, targetGuid, время, result), `positions[]`
(сэмплы координат игроков во времени), `map`.

Что используется (компактная выжимка в `data/raw/combat/`, сырой 1МБ не храним):

| Метрика | Из чего | Куда идёт |
|---|---|---|
| полученный урон/сек | сумма `players[g].taken` / duration | перформанс танков (меньше = лучше, сравнение среди всех танков на боссе) |
| смерти | `len(players[g].deaths)` | штраф к перформансу |
| перебивания / диспелы | `casts` с id/именем из `config/combat.yml` | бонус-утилити (перцентиль внутри роли) |
| расходники | `players[g].auras` с id из каталога | штраф за отсутствие (safety-valve, по умолчанию выкл) |

Перебивания/диспелы/расходники опознаются каталогом `config/combat.yml` — выжимка хранит
`casts`/`auras`, поэтому каталог правится и пересобирается без перекачки логов. Что не
опознано — не учитывается (не штрафует). Подтверждено вживую: у танка `taken` = 401 558.

## Другие найденные эндпоинты (не в пайплайне, на будущее)

```
GET /api/base/{realm}/guild/{guildId}       → guild, ranks, members (серверный ростер, ранги)
GET /api/base/{realm}/character/{name}       → character, equipments (надетое: entry+слот+ilvl)
```

`character.equipments` — текущая экипировка (ТЗ считало её недоступной). Для атрибуции лута
НЕ используется (нестабильно: игрок мог не успеть надеть), но это будущий источник для
прокси нужды по слоту (7.5) через реальный ilvl слота. `guild.members` — будущий источник
для сверки ростера.

## Что зафиксировано для следующих этапов

- Нормализатор (этап 2) пишем на подтверждённой схеме: время кила = `killed_at`/`timeEnd`,
  серверное локальное; участие — по `players[].name` → roster; размер — `player_count`.
- Ключ босса для перформанса (этап 3) = `(mapId, encounter_id)` или `boss_name`
  (оба в наличии). Ключ спека = `(class_id, spec)`.
- Слоты предметов (этап 4) тянем из карточек, в дропе их нет.
- `set_bonus` считаем по реальному `itemset[]`, а не по эвристике.
